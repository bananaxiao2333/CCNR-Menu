# 02 · 背景与动画

> 背景是这个模组的主功能。「怎么放一段小动画当背景」有四种做法，代价差别很大，本文讲清取舍与实现。

---

## 0. 背景铺在哪些界面上

- **主菜单**（替换原版全景图界面）；
- **所有「泥土背景」的原版界面**：世界选择、多人列表、设置、语言、辅助功能、Mod 列表、连接中……
  由挂在界面自己 `renderables` 列表最前面的一件 `ScreenBackgroundRenderable` 盖上去；
  它落在「原版画完泥土 → 原版控件」之间，所以既盖住泥土、也不压住选项列表
  （为什么不用 `ScreenEvent.BackgroundRendered` 见 docs/00 §4.1）；
- **世界内的界面**（暂停、背包、箱子、死亡界面）**不动**——它们的背景是玩家眼前的世界。
  想改这个范围见 `applyToAllScreens`（docs/03 §1）。

判定只有一份（纯类 `BackgroundScope`），两个绘制点共用，`BackgroundScopeTest` 覆盖四档组合。

## 1. 五种背景类型的取舍

| 类型 | 运行时开销 | 内存 | 制作难度 | 适合什么 |
| --- | --- | --- | --- | --- |
| `slideshow` | 每帧 1~2 次 blit | **同时 2 张** | 最低（丢几张照片） | 多张照片轮播，菜单最常用的那种「活的背景」 |
| `image` | 每帧一次 blit | 整张图 | 最低（截图即可） | 静态海报、风景图 |
| `sheet` | 每帧一次 blit（换 UV） | 整张图 | 中（要拼图，见 §4） | **推荐的动画方案**：循环小动画 |
| `gif` | 每帧一次整图上传（几百 KB~MB） | **宽×高×4×帧数** | 最低（导出即用） | 手上只有 GIF、帧数不多的场合 |
| `vanilla` | 原版全景 | 原版 | — | 退路，以及所有失败情形的兜底 |

**为什么把 `sheet` 列为推荐（对它适用的场合）**：精灵图是一张普通 PNG，逐帧只换采样区域（UV），
每帧**零解码、零上传**，全部由 GPU 采样完成。GIF 则必须每帧把像素写进动态贴图再上传——
一个 640×360 的 GIF 每帧上传约 900KB，10fps 就是 9MB/s 的持续带宽。
两张图观感完全一样，代价差一个量级。

**为什么仍然要做 GIF**：GIF 是「导入即用」的那条路——不需要任何拼图工具，
网上存下来丢进配置目录就能看。这条路的代价被两层机制压住了：**内存预算**（§3）与**逐帧懒转换**（§3）。

## 1.1 `slideshow`：多图轮播

用户要的效果是「几张照片轮着放，切换的时候淡出，每张再放大一点点并缓慢往右偏移」。
四件事分开配置，因为它们的调法互不相干：

| 配置 | 管什么 |
| --- | --- |
| `slides` | 哪几张图（顺序就是播放顺序） |
| `holdMs` / `fadeMs` | 节奏：每张停多久、末尾用多久交叉淡入 |
| `zoom` / `panX` / `panY` | 运镜：每张图自己在这段时间里放大多少、往哪偏多少 |
| `loop` | 播完回到第一张，还是停在最后一张 |

### 为什么运镜是「每张各自从头走一遍」

如果按整条时间轴连续运镜，切到第 5 张时画面已经放大到 1.4 倍了——那张图一出现就是糊的。
每张各自从 1.0 倍开始，才有「这张照片正在被缓慢推近」的感觉。
偏移同理，而且偏移量按**屏幕尺寸的分数**算而不是按图片像素算：
同一份配置在 1080p 与 1440p 上观感一致（作者调的是「大概移动屏幕宽度的 5%」）。

### 时刻表与边界连续性

时刻表在纯类 `ui/SlideTimeline`：第 i 张的周期是 `[i*holdMs, (i+1)*holdMs)`，
淡出排在周期的最后 `fadeMs`。这样「上一张的淡出」与「下一张的淡入」天然是同一段时间。
交叉淡入的画法是「先画当前这张，再按 `fade` 的 alpha 画下一张」——
结果正好是两者的线性插值，不需要同时把两张都设成半透明（那会让中间瞬间露出背景）。

有一个容易写错、但只有肉眼能发现的地方：**周期边界上进度必须接得上**。
`SlideTimeline` 里「下一张的进度」在淡入窗口末尾正好等于「它成为当前那张时的进度」，
否则换图的那一帧画面会猛地缩一下。`SlideTimelineTest` 专门断言了这一条。

### 内存与卡顿

- 屏幕上任何时刻最多看得见 2 张，所以只保留「当前 + 下一张」两张贴图，
  切换完成后立刻释放其余。否则 11 张 1920×1080 的贴图就是 90MB 显存。
- 下一张在**上一个停留周期开始时**就丢给工作线程解码。1920 宽的 JPEG 解码+上传要几十毫秒，
  放在切图那一帧上就是一次肉眼可见的顿；提前 9 秒开始，工作线程绰绰有余。
- 线程边界与 GIF 一致：工作线程只做纯计算（`FileTexture.decodeFile`），
  建贴图与上传经 `Minecraft.execute` 回到渲染线程（`FileTexture.fromImage`）。
- 一张都没就绪时画原版全景图（第一张是构造时同步加载的，这条兜底只在图片全挂了时才看得到）。

### 素材怎么来

`scripts/make-icon-presets.py` 把源图压成 1920 宽的 JPEG（质量 82，单张 160~330KB）
放进 `presets/slides/`，**共 11 张（合计 2.7MB）**。源图清单写死在脚本的 `SLIDE_SOURCES` 里：
编号即轮播顺序，清单里缺一张脚本直接报错退出。
为什么不用 glob 扫目录：实测 `~/Downloads` 里躺着 4 张无关的 8 月图片，一条
`QQ图片*.png` 会把它们一起塞进轮播，而且编号还会随文件名排序变化。
换照片时用 `--only-slides`，不必重跑 162 次无头 Chrome 截图。

## 1.2 泥土页面上的标志（`mark`，默认右下角水印）

模组一装上，设置 / 单人游戏 / 多人列表这些泥土页面就只剩一张背景图，一点机构标识都没有，
而它们和主菜单一样是玩家第一眼看到的东西。`mark` 就是补这一块的：

```json
"mark": {
  "file": "logo_wide_mono.png",
  "width": 420,        // 不给就按原图宽度，高度按原图比例算
  "opacity": 1.0,
  "x": 0.5, "y": 0.5,  // 分数锚点，默认正中
  "onMainMenu": false  // 默认只画在泥土页面上
}
```

三个设计决定：

- **为什么不做成「任意元素列表」**：那需要把主菜单整套布局与绘制搬进背景钩子里，
  而实际需求就是「放一个白色横版 logo」。等真要往泥土页面上加按钮时再升级形状，
  比现在就猜一套通用模型便宜得多。
- **为什么位置是「锚点分数 + `align`/`valign`」**：作者说的是「右下角、不贴边」——
  这是「标志的**右边缘**在 98%、**下边缘**在 95%」，而不是「标志的中心在 0.98/0.95」
  （后者会有一半跑到屏幕外）。所以锚点语义必须能选边，默认仍是居中，老配置一个字都不用改。
- **为什么默认不画在主菜单上**：主菜单左列里已经有一个图标了，正中间再叠一个就是两个 logo 打架。
- **绘制顺序是「背景 → 压暗层 → 标志」**：压暗层是给文字让路的东西（高亮背景会让白字看不清），
  标志要是画在它下面就会被一起压暗——一个白色 logo 被压成灰的，看起来像没加载出来。

标志画在**原版控件之前**（背景 Renderable 里），所以设置页面上它会落在选项列表下面。
这是刻意的：水印不该盖住按钮。

## 2. 曾经考虑过的方案（以及为什么否掉）

| 方案 | 否掉的原因 |
| --- | --- |
| 内嵌浏览器渲染 HTML/CSS/JS（MCEF 一类） | 客户端首次启动要从网上下载 Chromium 原生库（上百 MB），Linux/macOS/Windows 各一套；对一个「换菜单背景」的需求来说太重，而且离线/内网环境直接不可用 |
| 视频背景（MP4/WebM） | 同样要拖原生解码器与解复用库；解码成本远高于 GIF；一个 3 秒的循环视频对菜单背景是杀鸡用牛刀 |
| 逐帧上传 GIF 的每一帧到独立贴图 | 显存里躺着 N 张贴图，且每帧都在创建/销毁 GPU 资源；正确做法是一张贴图重传像素 |
| 用 `NativeImage.read()` 解 GIF | 它只认 PNG（stb_image）。GIF 必须走 ImageIO，这是本模组唯一用到的「非 MC 图形栈」 |

## 3. GIF：内存预算与播放

### 3.1 为什么必须有预算

GIF 的**文件体积**与**解压后的内存**完全不成比例：

| GIF | 解压后 |
| --- | --- |
| 640×360，20 帧 | 640×360×4×20 ≈ 18MB |
| 1920×1080，60 帧 | 1920×1080×4×60 ≈ **475MB** |

玩家从网上随手存一张动图丢进配置目录，就足以把游戏拖进 GC 风暴甚至 OOM——
而报错只会说「内存不足」，指不到那张图上。

因此 `GifBudget.scaleFor` 在**解码之前**按 `宽×高×4×帧数` 估算，
超预算就整倍缩小边长（**帧数与帧时长一律不动**，动画节奏不变）：

- 默认预算 96MB；
- 单边上限 4096，帧数上限 600，缩放倍数上限 16；
- 1920×1080×60 帧 → 缩到 1/3（640×360，约 55MB）；
- 即使缩到上限仍然超预算 → **拒绝解码**，日志里给出尺寸/帧数与建议。

用整倍缩小（而不是「缩到某个固定宽」）是为了让最近邻采样稳定：
非整倍缩放会让每一帧的采样点漂移，快速播放时表现为「边缘有细碎的抖动」。

### 3.2 逐帧懒转换

把 N 帧一次性转成 `NativeImage` 会在打开菜单的瞬间做 N×宽×高的像素搬运
（1080p×60 帧约 1.2 亿次操作，肉眼可见地卡一下）。

本模组的做法是**用到哪帧转哪帧**（`GifBackground.uploadFrame`）：
第一次播放到某帧时才转换（单帧约 0.1~1ms），10fps 的动画在头一秒内就把所有帧转完了，
而每一帧的代价都小到看不出来。

### 3.3 解码正确性：部分帧与 disposal

优化过的 GIF（ezgif 之类的工具默认就会这么做）**只把「与上一帧不同的那一小块」写进帧里**，
靠画布上残留的内容拼出完整画面；再叠加每帧的 `disposalMethod`：

| disposal | 含义 | 本项目的处理 |
| --- | --- | --- |
| 0 / 1 | 不处理 | 画布保留这一帧的内容 |
| 2 | 还原成背景 | 把这一帧占的矩形清成透明 |
| 3 | 还原成上一帧 | 整幅画布还原成「画这一帧之前」的快照 |

只读「第一帧」或「每帧独立」的朴素实现会得到一堆碎片，而且**只有动图才会暴露**
（静态看第一帧是好的）。实现与逐条测试见 `GifComposer` / `GifComposerTest`。

另外两个细节：

- **透明像素不覆盖画布**：GIF 的透明索引意思是「这里保持原样」，不是「这里涂透明」；
- **帧坐标可能超出逻辑屏幕**（损坏的 GIF）：越界像素直接丢弃，不能让它写坏数组。

### 3.4 帧时长

GIF 的 `delayTime` 单位是 1/100 秒，允许每帧不同（手绘动画常用长停留的关键帧）。

- `< 20ms` 的帧按 **100ms** 处理：大量导出工具会写 0（意思是「越快越好」），
  照字面执行会变成一秒几百帧的闪烁。浏览器也是这么做的，这样观感才一致。
- 播放用 `FrameTimeline`（变长帧计时）而不是 `FrameClock`（定长）。

## 3.5 图标（image 元素）的动画

图片元素也支持序列帧（`animation`，与背景共用解析）。本模组的默认图标就是这么来的：
CCNR 横版图标的入场动画在源文件里是 **CSS `@keyframes`**，Minecraft 不认识 SVG 也跑不了 CSS，
因此在**构建/生成期**用无头 Chrome 逐帧截成 80 张、拼成 8×10 的精灵图
（`scripts/make-icon-presets.py`），运行时只是一张 PNG + 换 UV。

三个容易踩的点：

1. **宽高比要按单帧算**：整张精灵图是 4096×1710（≈2.4:1），而单帧是 512×171（≈3:1）。
   用整图比例去算，图标会被压扁一半——配置里只写 `width`，高按单帧比例自动出来。
2. **入场动画要 `loop: false`**：图标设计的原意是「播一次后停在末帧」，
   循环播放会让人一直盯着它重播。
3. **帧率受贴图边长限制**：每帧 512 宽 → 一行最多 8 列（8×512 = 4096，正好顶到
   `FileTexture.MAX_DIMENSION`），要更多帧只能加行。
   当前是 8×10 = 80 帧 / 2.6s ≈ **30fps**（整张贴图约 28MB 显存）。
   上一版是 8×4 = 32 帧 ≈ 12.3fps，入场那几下快动作（pop / draw）能看出顿——
   **帧率是这类「一次性入场动画」最容易省错的地方**：静态帧数看不出来，动起来才知道。

生成脚本还会注入一条 `theme-mono` 规则（`--ccnr-ink` 与 `--ccnr-accent` 同时覆写成
`#FFFFFF`）产出**全白单色**一套。`mono` 不是源 SVG 里已有的主题，是脚本加的：
源文件只读，不改。校验方式是数出来的——全白版非透明像素 64160 个，
不同 RGB **只有 1 种**（`#FFFFFF`），且与彩色版逐像素覆盖数完全一致（形状没被改）。

## 4. 怎么做精灵图（`sheet`）

1. 导出逐帧 PNG（帧数建议 8~60，每帧尺寸一致）；
2. 拼成网格：`cols` × `rows`（行优先，从左上角开始）；
3. 配置里写网格与帧时长：

```json
"background": {
  "type": "sheet",
  "file": "bg.png",
  "fit": "cover",
  "animation": { "cols": 8, "rows": 4, "frames": 30, "fps": 20, "loop": true, "speed": 1.0 }
}
```

- `frames` 可以小于 `cols*rows`（末行留空是常见做法）；
- `fps` 与 `frameMs`（每帧毫秒）二选一，`speed` 是整体倍速；
- **贴图尺寸最好是格数的整数倍**：不是整数倍时，每一格的尺寸用整数除法取（最后一格贴住右下角），
  这样不会出现「格子边界落在半个像素上、把邻格内容吸进来」的抖动。

## 5. 常见现象与原因

| 现象 | 原因 |
| --- | --- |
| 背景是原版全景图 | `background.type` 不是动画类型、或文件不在 `config/ccnr_menu/`、或解码失败——看 `/ccnr_menu status` 与日志 |
| 图片四周有黑边 | `fit: contain`（等比完整可见，必然留边）。想铺满改成 `cover` |
| 图片被拉伸变形 | `fit: stretch`。改 `cover` 或把图做成屏幕比例 |
| 画面上多了一层灰 | `theme.backdrop`（默认 40% 黑）。它是文字可读性的保障，可以去 `/ccnr_menu` 里调小 |
| GIF 只有第一帧动 | 解码失败（看日志）——注意 `4000×4000×600 帧` 这类超限的 GIF 会被拒绝 |
| 动画忽快忽慢 | 不会有这种情况：播放由绝对时间决定，与帧率无关（见 `FrameClock` 的类注释） |
| 轮播一直停在第 0 张 | `slides` 里的文件不在（`/ccnr_menu status` 会逐张列出 `[文件不存在]`），或 `holdMs` 配得极大 |
| 轮播切图时卡一下 | 只可能是那一张的解码没赶上——正常情况下它在上一个周期就解好了。看日志有没有「轮播素材加载失败」 |
| 轮播在图还没好时闪一下原版 | 第一张加载失败的兜底（背景钩子会先画原版全景图） |
| 泥土页面上没有白色图标 | 没写 `mark`，或 `mark.file` 不在配置目录，或 `onMainMenu` 挡掉了主菜单上的那一份 |
