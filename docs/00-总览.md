# 00 · 总览

> CCNR-Menu 的定位、架构、包布局与关键数据流。改代码前先读本文。

---

## 1. 定位

**CCNR-Menu** 是**纯客户端**的主菜单自定义模组：用一份 JSON 配置决定主菜单长什么样。

与另外几个 CCNR 仓库的关系：

| 仓库 | 关系 |
| --- | --- |
| CCNR-RP | **无依赖**。共用工程规范与视觉纪律，代码互不引用 |
| CCNR-PM | **无依赖**。同上 |
| CCNR-Com | **无依赖**。同上 |
| CCNR-Data | 无关（本模组不联网、不上报） |

**为什么坚持独立**：菜单外观是纯粹的客户端偏好。任何服务器都可能只想要「换个背景」，
不该被拖进一整套 RP/管理系统的依赖里。反过来，本模组的改动也不会影响到别人。

## 3. 包布局

```
com.ccnrcom.menu
├── CCNRMenuMod               入口：判 dist（服务端直接退出），启动时读一次配置并打日志
├── config
│   ├── MenuConfig            配置根对象（enabled / vanillaButtons / background / theme / elements）
│   ├── BackgroundSpec        背景定义（类型 / 文件 / fit / tint / opacity / 序列帧 / 轮播列表）
│   ├── SlideSpec             轮播的节奏与运镜（停留 / 淡入 / 放大 / 偏移 / 循环）
│   ├── MarkSpec              泥土页面正中间的标志（文件 / 宽度 / 不透明度 / 位置）
│   ├── MenuElement           元素定义（button/label/image + 锚点 + 尺寸 + 颜色）
│   ├── MenuThemeSpec         配色与按钮外观（三态颜色 / 强调色 / 压暗层 / buttonStyle）
│   ├── MenuDefaults          历史默认配置清单（版本 → 原文，升级迁移的唯一依据）
│   ├── MenuAction            动作枚举 + **白名单校验**（screen / connect / url / copy / quit）
│   ├── MenuConfigIO          读写 config/ccnr_menu/（原子写、缺省生成、素材路径越界拦截）
│   └── MenuConfigStore       客户端持有的当前配置（mtime 变了才重载）
├── ui                         ★ 纯逻辑（无 MC import，直接 JUnit 测）
│   ├── MenuGeometry          摆放与缩放：fit（cover/contain/…）、锚点、精灵图 UV、平铺次数
│   ├── FrameClock            定长帧计时（精灵图用）
│   ├── FrameTimeline         变长帧计时（GIF 每帧时长不同）
│   ├── SpriteSheet           精灵图参数（网格 → 帧数 / 帧时长 / 行列）
│   ├── ColorSpec             颜色解析（#RGB/#RRGGBB/#AARRGGBB）+ 通道读写
│   ├── SlideTimeline         轮播的时刻表（该画哪张 / 淡到几分 / 每张走到第几步）
│   ├── ButtonStyle           按钮外观枚举（solid 有底色 / text 无背景纯文字）
│   ├── Align / VAlign / Fit  三种枚举 + 大小写不敏感解析
├── gif                        ★ 纯 Java GIF 解码（只用 JDK 自带 ImageIO）
│   ├── GifDecoder            解码全部帧（部分帧合成、disposal、透明、越大越缩）
│   ├── GifComposer           画布合成（透明不覆盖、清块、整倍缩小）
│   ├── GifBudget             内存预算（解码前先算清，超了就整倍缩小）
│   └── GifFrames             解码结果（宽高 + 每帧 ARGB 像素 + 逐帧时长）
├── client                     仅客户端
│   ├── MenuScreen            ★ 主菜单屏幕（背景 → 压暗 → 图片 → 文字 → 按钮）
│   ├── TitleScreenHook       ScreenEvent.Opening → 把 TitleScreen 换成 MenuScreen（无 mixin）
│   ├── ScreenBackgroundHook  ScreenEvent.Init.Post → 给泥土界面挂一件画背景的 Renderable
│   ├── MenuActions           动作执行（界面映射 / 直连 / 打开链接 / 复制 / 退出）
│   ├── background
│   │   ├── ScreenBackgrounds  ★ 全模组唯一的背景持有者（按配置指纹共享 + 进入世界释放）
│   │   ├── BackgroundScope    纯函数：哪些界面该被接管（含世界内界面豁免）
│   │   ├── BackgroundRenderer  接口（render / ready / close）
│   │   ├── BackgroundFactory   ★ 唯一的降级收口处（素材缺失 → 原版全景图）
│   │   ├── VanillaBackground   原版全景图（也是所有失败情形的兜底）
│   │   ├── ImageBackground     静态图片
│   │   ├── SheetBackground     精灵图序列帧（GPU 直绘）
│   │   ├── GifBackground       动画 GIF（工作线程解码 + 逐帧懒转换 + 每帧上传）
│   │   ├── SlideshowBackground 多图轮播（只留当前+下一张贴图，下一张提前一个周期异步解码）
│   │   ├── MarkRenderer        泥土页面正中间的标志（贴图懒加载，压在压暗层之上）
│   │   ├── ColorBackground     纯色 / 黑屏
│   │   └── TextureDraw         ★ 铺屏与 blit 的**唯一**画法（fit/平铺/着色/复位）
│   ├── texture
│   │   └── FileTexture         游戏目录外的图片 → 动态贴图（含 ABGR 字节序换算与释放）
│   └── ui
│       ├── MenuTheme           绘制令牌 + 共享入口（禁止界面代码里写裸色值）
│       └── MenuButton          AbstractWidget 子类（白送键盘导航与旁白）
└── command
    └── MenuClientCommand      /ccnr_menu status|reload|open|where（客户端命令）
```

**纯类（无 MC import，可直接 JUnit 测）**：整个 `ui` 包、整个 `gif` 包、`config` 里的
`MenuConfig` / `BackgroundSpec` / `SlideSpec` / `MarkSpec` / `MenuElement` / `MenuAction` /
`MenuThemeSpec` / `MenuDefaults`。
规则与几何逻辑尽量放在这一层——项目禁止起客户端做验证，全仓库的可测性都来自这里。

## 4. 数据流

```
config/ccnr_menu/menu.json
        │  MenuConfigIO.load()（缺失则生成默认模板；损坏则留 .bak 并兜底）
        ▼
   MenuConfig ──────────────► MenuConfigStore（客户端当前配置，mtime 变化时重载）
        │                                   │
        │ 打开主菜单时（TitleScreenHook）    │ /ccnr_menu reload
        ▼                                   ▼
   MenuScreen(config)
        ├── BackgroundFactory.create(spec) ──► BackgroundRenderer（image / sheet / gif / vanilla）
        ├── elements → MenuButton（widget）/ PlacedLabel / PlacedImage
        └── render(): 背景 → 压暗 → 图片 → 文字 → 按钮
```

**背景素材的两条路**：

- **静态图 / 精灵图**：`FileTexture.load()` 在渲染线程同步解码 → 注册成动态贴图 → blit。
- **动画 GIF**：`GifBackground` 起 `ccnr-menu-gif` 线程解码（纯计算，不碰 GL）→
  解完 `Minecraft.execute(...)` 回渲染线程建贴图 → 播放时**用到哪帧转哪帧**。

### 4.1 背景有两个绘制点，但只有一份实现

| 绘制点 | 时机 | 覆盖的界面 |
| --- | --- | --- |
| `MenuScreen.render` | 自己画（不能调 `super.render`，它会画泥土） | 本模组的主菜单 |
| `ScreenBackgroundRenderable` | 挂在界面 `renderables` 的**下标 0**：原版先 `renderBackground()` 画泥土，再遍历 `renderables` | 原版那些**泥土背景**界面 |

两者都调 `ScreenBackgrounds.render(...)`，判定都走 `BackgroundScope`：
主菜单只要启用就接管，泥土界面看 `applyToAllScreens`，而**世界内的界面永不接管**
（背景是玩家眼前的世界，盖掉会失去空间感）。

原版界面那条**没用** `ScreenEvent.BackgroundRendered`（更「正统」的那个钩子）：实测所有二级界面
都还是泥土，而日志没有报错、事件本身也确实会被原版 `renderDirtBackground()` 发出来。
现在这条路不依赖任何事件派发，只要界面走正常流程就一定生效；`ScreenBackgroundHook` 对每种界面
打一行 INFO（`已接管界面背景` / `未接管界面背景（原因）`），「没生效」不再是无声的。

### 4.2 背景的所有权：按指纹共享

`ScreenBackgrounds` 用「背景全部参数 + 素材文件修改时间」组成指纹，指纹没变就复用同一个
`BackgroundRenderer`。于是：

- 主菜单 → 设置 → 返回主菜单**不会**两次解码同一张 GIF（旧实现会）；
- 改配置或换素材文件 → 指纹变化 → 自动重建（不必重启，也不必手动清缓存）；
- **进入世界**时释放（`ClientPlayerNetworkEvent.LoggingIn`）：进游戏后几乎不会再出现泥土界面，
  这时把几十 MB 的动画帧交还系统，下次需要时按需重建。

## 5. 生命周期与所有权（对称清理）

| 资源 | 创建 | 释放 |
| --- | --- | --- |
| 背景绘制器（含贴图 / 解码帧） | `ScreenBackgrounds.ensure()`（指纹变化时才建） | `ScreenBackgrounds.release()`（进入世界时；指纹变化时换掉旧的） |
| 元素图片贴图 | `MenuScreen.init()` | `MenuScreen.removed()`；`init()` 重跑时先释放上一轮 |
| GIF 解码线程 | `GifBackground` 构造 | 线程自行结束；结果若在屏幕关闭后到达则**直接丢弃** |

两条硬规则：

1. **`init()` 与 `removed()` 不对称是刻意的**：`init()` 会因窗口缩放/资源重载反复调用，
   而 `removed()` 只在屏幕被替换时调用一次。背景只在 `init()` 里建一次、只在 `removed()` 里释放，
   所以缩放窗口不会重新解码 GIF。
2. **屏幕关闭就释放**：一张动画背景解码后可能几十 MB，不该跟着玩家进游戏世界。
   代价是「回到主菜单要重新解码一次」——这个代价值得。

## 6. 服务端行为

Forge 1.20.1 的 `mods.toml` **没有** `clientSideOnly` 字段（1.20.2+ 才加入），
所以这个 jar 在专用服务端上也会被加载。处理方式是在入口直接判 `FMLEnvironment.dist`：
服务端上一个配置文件都不读、一个客户端类都不加载；`Dist.CLIENT` 标注的事件订阅者
由 Forge 自己跳过。

因此：**服务端不需要装也不会因为客户端装了而报错**。

## 7. 刻意不做的事

| 不做 | 原因 |
| --- | --- |
| 接管世界内的界面背景 | 暂停/背包/箱子的背景是玩家眼前的世界；盖掉它玩家会失去空间感（`BackgroundScope` 有专门的测试守着） |
| HTML/浏览器渲染 | 要拖进 Chromium（MCEF 一类）与上百 MB 原生库，与「轻量导入小动画」的目标直接冲突 |
| 视频背景 | 同样要拖原生解码器（FFmpeg 一类），且解码成本远高于 GIF/精灵图 |
| 视频/多背景叠加 | 现有五种类型已覆盖实际需求；叠加顺序是另一个设计问题，先不引入 |
| 往泥土页面上放任意元素 | `mark` 只支持一个居中图片。要做按钮就得把主菜单那套布局搬进背景钩子，等真需要再说 |
| 改暂停菜单 / 死亡界面 | 本模组只声称管主菜单。要做就得先定义「每个界面各自的背景与元素」这套模型 |
| Realms 按钮 | 界面类 `RealmsMainScreen` 不在客户端 jar 里，只能用反射，代价是「点了崩在哪里」说不清 |

## 8. 随模组发布的内置素材

`assets/ccnr_menu/presets/` 里的图**不是手绘的**，而是从 CCNR 图标的 SVG 主动画
（CSS `@keyframes`）**预渲染**出来的，生成脚本是 `scripts/make-icon-presets.py`
（无头 Chrome 逐帧截图 → 无依赖的 Python PNG 拼接 → 8×10 精灵图，80 帧 ≈30fps）。

| 文件 | 内容 |
| --- | --- |
| `background.png` | CCNR 背景图（1920×1080 原样拷贝） |
| `logo_wide_mono.png` / `logo_wide_intro_mono.png` | **全白单色**（脚本注入的 `theme-mono`：ink 与 accent 同时覆写成 `#FFFFFF`） |
| `logo_wide_white.png` / `logo_wide_intro_white.png` | 浅色图形 + 品牌青（源文件的 `theme-dark`），配深背景 |
| `slides/01.jpg` … `slides/11.jpg` | 轮播照片：`~/Downloads/` 的 11 张源图压到 1920 宽的 JPEG（合计 2.7MB，编号即轮播顺序） |

首次运行 `MenuConfigIO.ensureDefaults()` 会把它们释放到 `config/ccnr_menu/`，
**已存在则跳过**（绝不覆盖作者自己的文件）。`PresetAssetsTest` 双向对齐
「配置引用的素材名」与「资源目录里真实存在的文件」。
